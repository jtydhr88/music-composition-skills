# music-composition-skills（作曲・編曲スキル集）

[English](README.md) · [中文版](README_ZH.md) · 日本語 · [한국어](README_KO.md)

ポピュラー音楽の作曲と編曲のためのエージェント・スキル 29 個（[Claude Code](https://docs.anthropic.com/en/docs/claude-code/skills) と [OpenAI Codex](https://developers.openai.com/codex/) 向け）。管弦楽法・和声・楽式・対位法・ミックス・各ジャンル実務を扱う 50 冊の本に、マルチトラック音源から実測した 62 曲のアレンジを加えて抽出したものです。

`SKILL.md` はオープン規格 [agentskills.io](https://agentskills.io) に従っており、両方のエージェントが同じファイルを共有します。一度入れれば、どちらでも動きます。

**出てくるのは助言ではなく、一枚の仕様書です。** 曲を頼むと、エージェントが埋めるのは ARR-SPEC——キー、テンポ、小節単位のセクション表、コードネームとローマ数字の度数表記、誰がいつ入っていつ抜けるか、エネルギーカーブ、ボーカルの歌わせ方、ミックス意図——そして、その一枚をそのまま Suno のプロンプト、YuE2 向けの ABC 譜、あるいは MIDI へコンパイルします。出来上がりを照合するのも同じ一枚です。設計はこの一点に尽きます——**一つの成果物を四通りに使う**：外部への引き継ぎ、条件を揃えた A/B、コンパイル元、受け入れ基準。

**自分の言語で聞いてください。** スキル本文は中国語で書かれています。底本の大半が中国語の原著か中国語訳だからです。どの言語で聞いても、エージェントはその言語で答えます。

**このスキル群は生成モデルを速くはしません。時間と引き換えに品質を取る仕組みです。** プロの音楽制作ワークフローを一通り回すと、一曲に二十分以上かかることも珍しくありません（agent が判断基準を読み、仕様書を埋め、自己点検を通すため）。その代わりに得られるのは、数行のプロンプトではなくプロ水準の仕様書です。

**本ライブラリは作品を一切収録していません。作者自身のものも他のアーティストのものも、編曲も歌詞もありません。** 音楽作品の良し悪しは主観的な判断です。ご自身で使い、その価値と、時間という代価をご自身で判断してください。

## このシリーズの四つの library

一本のオーディオ・ラインを、独立した四つの library に切り分けています。それぞれ単独で使え、継ぎ目が明文化されているので組み合わせても使えます。

| Library | 何をするか | 状態 |
|---|---|---|
| **[music-composition-skills](https://github.com/jtydhr88/music-composition-skills)** | 作曲と編曲。ブリーフを ARR-SPEC に変える：調、テンポ、セクション表、和声、誰がいつ入り退くか、エネルギー曲線、ボーカルとミックスの意図。Suno、YuE2、MIDI 向けの入力にコンパイルする | **この library** |
| **[lyric-writing-skills](https://github.com/jtydhr88/lyric-writing-skills)** | 作詞。立意の関門を LYR-SPEC に変える：構造、イメージ、韻、叙述、そして中国語（普通話・広東語）、英語、日本語、韓国語の言語層 | 公開済み |
| **映画音楽** | 映像に合わせて書く音楽：スポッティング、カットとの関係、cue の書き方と命名、テーマの映画全体での展開 | 予定 |
| **ミキシングとサウンドデザイン** | ミックスの意図を実際の操作に変える：EQ、コンプレッション、リバーブ、オートメーション、マスタリング | 予定 |

**独立している。** 既存のメロディに詞を当てるなら作詞 library だけで足りる。インストゥルメンタルを編曲するなら作編曲 library だけで足りる。

**名前のついた受け渡しで組み合わさる。** ARR-SPEC と LYR-SPEC は双方向で、曲先なら セクション表と小節数を渡し、詞先なら 行長と強勢位置を返す。六つのフィールドは両方向で一致しなければならない。ARR-SPEC の中の `mix_intent` は、ミキシング library がブリーフとして受け取るもの。映画音楽 library の cue sheet は、作編曲 library がブリーフとして受け取るもの。

**継ぎ目はすでに書かれている。** すべてのスキルが境界表を持ち、他の library に属する問いは その場で下手に答えずに名前で回される。だから予定中の二つの library はすでに随所で参照されている：EQ とコンプレッションの実務はミキシング library へ、スポッティングと cue の執筆は映画音楽 library へ。

## 生成モデルがあるのに、なぜこれが要るのか

Suno も YuE2 も、一文から「完成して聞こえる」曲をすでに作ってくれます。それらがやってくれないのは、一つの指示を二度、同じ形で返すことです。

生成モデルは、あなたが指定しなかった部分をすべて埋めます。しかも自分のデフォルト値で埋めます。世間が「AI っぽい」と聞き取るのは、そのデフォルト値そのものです——どのセクションも 8 小節の倍数、エネルギーは上がる一方、A メロからサビまで編成が一度も変わらない、終わりはフェードアウト、ボーカルは最初から最後まで同じ強さ。これはモデルの欠陥ではありません。誰も決定を下さなかった音です。

このライブラリが供給するのは、その決定です。現役のアレンジャーが下すのと同じ水準で決め、モデルに伝えられる形で書き出します——ギターが何小節目で抜けるのか、どのセクションが上がる直前に一層減らすのか、エネルギーはどこで落ちるのか、3 回目のサビでボーカルは何を変えるのか。**やっているのは、専門家水準の規則で生成モデルをディレクションすることです。生成モデルを作り直そうとはしていません。**

これで手に入るのは、プロンプトエンジニアリングでは届かない部分です。プロンプトは一文であり、一文はフィールドごとに照合できません。仕様書なら、返ってきたものとフィールド単位で突き合わせられますし、一度に一つのフィールドだけ変えて再実行し、条件を揃えた比較ができます。そこに書かれた決定にはすべて理由と出典が付いているので、半年後でも 2 回目のサビをなぜそう編曲したのか言えます。

モデルは演奏者でありスタジオのままです。これは、そこへ手渡すアレンジ譜です。

```

cp -r music-composition-skills/plugins/music-composition/skills/* ~/.claude/skills/
```

#### プロジェクト単位

```bash
mkdir -p .claude/skills
cp -r music-composition-skills/plugins/music-composition/skills/* .claude/skills/
```

codex plugin marketplace add jtydhr88/music-composition-skills

関連する文脈を検知すると、スキルは自動で読み込まれます。一覧を出すには `/skills`。

## よくある組み合わせ

見た目より複雑です。一行の brief が作曲・編曲・作詞の三方面で十数個の skill を動かし、エージェントが何を読み何を出すかは、その一行にいくつかの要点が入っているかで決まります。以下は実際に最後まで走らせた組み合わせです。言い方、通る skill、出てくるもの。歌詞のある用例は作曲編曲ライブラリと作詞ライブラリの両方が必要です。

**1. 特定のアーティストの作風で、歌詞付きの曲を書く**（最も多い）

> あるアーティストのある曲のような中国語ポップスを一曲、女性ボーカル、Suno で生成、歌詞付きで。

通る：lw-workflow → lw-song-intent → lw-structure → lw-mandarin → lw-tone-check → lw-suno-interface；mc-workflow → mc-style-chinese-pop → mc-melody → mc-development → mc-arrangement-arch → mc-vocal-direction → mc-render-compile
出る：LYR-SPEC.yaml、ARR-SPEC.yaml、suno-pack.md（タイトル、スタイル記述、セクションタグ付き歌詞、除外語）
注：参照アーティストから借りるのは編成・テンポ・ボーカルの人物像・セクションの運びだけ。詞と曲は借りません。

**2. 抖音向けのキャッチーな曲、物語なし**

> 抖音向けのキャッチーな曲を一曲、女性、甘め、物語はなし。Suno 生成、歌詞付き。

通る：lw-song-intent（態度型）→ lw-structure（反復予算、フックの位置）→ lw-rhyme → lw-mandarin；mc-style-chinese-pop → mc-rhythm-groove → mc-arrangement-arch → mc-render-compile
注：「物語はなし」の一言が歌詞の型を決めます。言わなければ既定で情景型になります。

**3. 悲しいラブソング、直接言う、情景なし**

> あるアーティストのある曲のような悲しいラブソング、男性ボーカル、Suno 生成、歌詞付き。直接言うタイプで、情景描写はなし。

通る：1 と同じ。ただし lw-song-intent は態度型を通り、錨は物ではなく一つの文（各サビの頭で繰り返す行）；mc-vocal-direction がオンマイクの男声と最後の一行の余白を担当
注：コーパスでは態度型の曲の四割に、写真に撮れる物が一つもありません。サビは「あなた」に向けた一文、A メロは自分の状態、冒頭は独白。これが欲しければ brief に「直接言う、情景も物もなし」と書きます。

**4. 一つの気分、物語にはしない**

> 中国語ポップスを一曲、三分半、女性ボーカル。テーマは、引っ越しの日に充電ケーブルを壁のコンセントに残したまま、二本先の通りで思い出して、取りに戻らなかったこと。物語にはしないで。思い出して、まあいいかとなる気分が欲しい。

通る：lw-song-intent（情景型、錨の物はケーブル）→ lw-imagery → lw-structure → lw-mandarin → lw-tone-check；曲側は 1 と同じ
注：情景型と物語型の境界はここです。物はあるが、筋は進まない。

**5. インストゥルメンタル、ゼロから作曲**

> 二分四十秒のインスト曲を、ショート動画の BGM に。主奏はナイロン弦ギター、少しのパーカッションとベース、鍵盤一台まで可。雰囲気は「午後三時、人を待っている、急いでいない」。ボーカルなし。

通る：mc-workflow → mc-development（動機、性格、発展の手法）→ mc-melody → mc-form → mc-harmony → mc-rhythm-section → mc-orchestration → mc-render-compile
出る：ARR-SPEC.yaml（material ブロックと各セクションの development を埋めたもの）、suno-pack.md、一枚の説明
注：歌詞がないので作詞ライブラリは関与しません。判定基準は mc-development にあります。新素材は半分未満、再現あり。

**6. 詞と曲は済み、編曲だけ**

> メロディと歌詞が出来ている中国語ラブソングを編曲して。サルサの感じで、ブラス入り、中速からやや速め。仕様書だけ、Suno プロンプトは不要。

通る：mc-workflow（編曲ルート）→ mc-style-latin → mc-rhythm-section → mc-orchestration（ブラス）→ mc-arrangement-arch → mc-texture-layering
出る：ARR-SPEC.yaml と一枚の説明のみ

**7. 融合：A メロはラップ、サビは中華風**

> ある曲のようなラップと中華風の曲を、完全な中国語歌詞付きで、Suno 用に。

通る：mc-workflow §2.4 スタイル融合 → mc-style-hiphop（ベース）+ mc-style-chinese-pop（オーバーレイ）；lw-rap（A メロ）+ lw-chinese-style（サビ）+ lw-mandarin

**8. 広東語の詞を既存のメロディに**

> このメロディに広東語の詞を付けて。小節数と各行の音数は添付。

通る：lw-workflow（曲先）→ lw-cantonese（まず音高クラスで計算、それから字を選ぶ）→ lw-tone-check
注：広東語は書く順序が逆で、北京語の層では代用できません。

**9. Suno ではなく、ローカルのオープンソースモデル（YuE2）**

> 同じ曲を Suno を通さず、ローカルの YuE2 で生成したい。仕様書を ABC 譜にコンパイルして。

通る：1 と同じ、加えて mc-symbolic-score（ARR-SPEC を ABC にコンパイル。ボーカル線は小文字音名の音域に、w: 歌詞行付き）
注：実験段階です。歌詞が歌われて聞き取れる割合は、スタイルと歌詞を直接渡す方式より今のところ低い。詳細は mc-symbolic-score §6b。

brief の中で実際に効いている文：

| あなたが言うこと | それが決めること |
|---|---|
| アーティスト名＋曲名 | 編成・テンポ・ボーカルの人物像・セクションの運びを借りる。詞と曲は借りない |
| 女声／男声、甘め／オンマイク | mc-vocal-direction の人物像と音域 |
| Suno ／ ローカル YuE2 ／ 仕様書だけ | 出口：suno-pack、ABC 譜、ARR-SPEC のみ |
| 物語なし ／ 直接言う情景なし ／ 物語にしない | 歌詞の型：態度型 ／ 物のない態度型 ／ 情景型。言わなければ既定は情景型 |
| 尺 | セクション数と小節数はここから逆算 |
| 成果物リスト | 欲しいファイルを書けば、エージェントはそのリスト通りに出す。一つ欠ければ未完 |

どれもフルで走らせると二十分以上かかります。上の「時間で品質を買う」の項を参照。

## ツールは一切不要

プラグインはプレーンテキストです。走らせるスクリプトはなく、Python も Node も不要、lint の工程もありません。このライブラリのチェックはすべて、あなたかエージェントが目で追える**チェックリスト**として存在します——`mc-workflow` §3.0 の 20 項目の仕様セルフチェック、`mc-ai-tell-audit` の 14 個の AI 臭フラグ、各スキル末尾の「終わる前に必ず通すこと」リスト。

**規則は判断基準であって、関門ではありません。** どこかが通らないときは、仕様を変えるか、この曲はなぜそうあるべきなのかを一行書くかのどちらかです。理由を書いた逸脱は正当な選択です。コンパイルを止めるものは、このライブラリの中に一つもありません。

## 多言語対応

**ソースは一つ、出力は実行時にどの言語でも。** スキルは中国語で一度だけ書かれていて、エージェントはあなたが尋ねた言語で答えます。フラグも、別インストールも、言語別のプラグインもありません。

スキル本文を他言語へ分岐させることはしません。これは手落ちではなく、決定です。姉妹プロジェクトの [screenwriting-skills](https://github.com/jtydhr88/screenwriting-skills) は完全な英語版を作り、本体に統合し、そのあと削除しました。そのとき決め手になった理屈は、ここでもそのまま成り立ちます——中国語を読めない人に翻訳ツリーが必要なら、英語を読めない人にも必要なはずで、次は日本語、その次は韓国語、さらにフランス語と続きます。本パックは 52 ファイル。4 言語なら 208 ファイルになり、それぞれ勝手にずれていき、どれが古いのかを教えてくれるものは何もありません。翻訳そのものは安い部分です。本当の代価は、一度分岐させてしまえば、二度目の分岐を断る筋の通った理由がなくなることです。

そのぶんを、実行時にこう肩代わりします。

- **出力言語は質問の言語に従います。** 日本語で聞けば日本語で返ります。アレンジ譜も、セクション名も、そこに至る理屈も、その言語で返ってきます。
- **用語は原語に固定します。** この分野の語彙は、もともと英語・イタリア語・ドイツ語・日本語の混成です——*tension*、*avoid note*、*comping*、*build*、*drop*、落ちサビ、打ち込み。底本の中国語じたいが訳語であり、訳者ごとに選択が違います。だから原語が概念と一緒に移動します。
- **対応する訳語がない用語は、原形のまま注釈を添えます。** 落ちサビ、符割り、類音階、十三辙（中国語の押韻分類）は、原語に短い説明を付けた形で出てきます。
- **あなたの譜面と歌詞は、その言語のままです。** 中国語の曲を英語で論じるのは普通のことです。切り替わるのは会話の言語であって、作品ではありません。

この方針が引き換えに手放しているのは、監査可能性です。中国語が読めなければ、指示ファイルそのものは読めません。読めるのは、エージェントがそれについて語った内容だけです。これは本物の代価であり、翻訳ツリーが本当に買えるものも、まさにそれだけです。それでも、あらゆる規則が検証可能な出典とページを持つことに価値の根拠を置くライブラリにとって、4 系統を永続的に保守する負担には見合いません。

**README は話が別です。** こちらは翻訳してあります。短く、内容が安定していて、新しく来た人が最初に目にするものだからです。

## スキルの構成

6 層構成です。ある層は自分より下の層しか知りません。そして各スキルは、自分が**担当しない**ことを明記した境界表を持っています——スタイル層が汎用の和声を黙って書き換えるのを止めているのは、その表です。

```
L0 ワークフロー   ルーター、ARR-SPEC 契約、融合時の分担、ステージ表
L1 汎用層         メロディ · 和声 · コード進行 · 転調 · リズム · 楽式 · 対位法
L2 アレンジ層     構成 · オーケストレーション · テクスチャー · リズムセクション · サウンドデザイン · ボーカル · ミックス意図
L3 スタイル層     J-POP · シティポップ & R&B · ジャズ · 華語ポップ · EDM · ロックバンド · シネマティック · ヒップホップ
L4 実行層         各バックエンドへコンパイル · 記譜出力 · AI 臭の診断
L5 コーパス層     教科書の規則を裏づける／覆す、実測された音源
```

### L0 — 入口

| スキル | 何を扱うか |
|---|---|

### L4 — 実行と検証

| スキル | 何を扱うか |
|---|---|
| `mc-render-compile` | コンパイラは一つ、バックエンドは複数。バックエンドの差は**データ**として `backends.yaml` に置く——各バックエンドがフィールドごとに `honors: exact / hint / none` を宣言し、実現できないフィールドは**0 点をつけるのではなく採点から除外する**。モデルを一つ足すのは、スキルを足すことではなくデータブロックを足すこと |
| `mc-symbolic-score` | ARR-SPEC から ABC、MusicXML、MIDI を一つのエミッタで出力。この経路では、仕様は「ほのめかされる」のではなく**実行される** |
| `mc-ai-tell-audit` | 機械が作った音楽に出る 14 個の列挙可能な兆候を、一つずつ数える。二つの数字を意図的に分けたまま扱う：*バックエンドは仕様どおりにやったか* と *結果に機械の指紋が残っているか*——前者が満点でも後者に落ちる曲はある |

### L5 — コーパス

| スキル | 何を扱うか |
|---|---|
| `mc-case-studies` | 音源に証言させる方法。マルチトラック音源から実測した 62 曲のアレンジを ARR-SPEC として書き戻してあるので、教科書の主張を意見ではなく的中率と突き合わせられる。キュレーションではなく自然抽出——コーパスをキュレーションすれば、自分が既に信じている規則の側に偏る |

| ファイル | 中身 |
|---|---|

## 体裁と方針

- `SKILL.md` のフロントマター：`name`（ケバブケース、フォルダ名と一致）と、"Use when …" で終わる長めの英語 `description`。中国語のキーワードを併記してあるので、どちらの言語でもルーティングが効きます。
- 本文は中国語。番号付きの原則、表、チェックリスト。出力言語は質問の言語に従います。
- **すべての規則に、失効条件かセルフチェックの動作が付いています。** テストできない規則は、ただの意見です。
- 出典同士が食い違うところは両論併記し、それぞれどんな場面で当てはまるかを注記してあります——Levine のコードスケール判断と日本のポップス実務、Drummer's Bible のテンポ帯と Groove Essentials が数字を出すのを拒む姿勢。
- コードは必ず二重表記：コードネーム**と**ローマ数字の度数、既定のキーは C。
- 引用には出典とページを付けます。単一の出典しか根拠がない主張は、そう明記します。
- 長い表と作例は `reference.md` に置き、`SKILL.md` は 40 KB 未満に保ちます。
- 設計上エージェント非依存：スキルファイルはどのエージェント名も出さず、エージェント固有の構文も使いません。
