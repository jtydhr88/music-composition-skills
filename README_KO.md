# music-composition-skills (작곡·편곡 스킬 모음)

[English](README.md) · [中文版](README_ZH.md) · [日本語](README_JA.md) · 한국어

대중음악의 작곡과 편곡을 위한 에이전트 스킬 29개([Claude Code](https://docs.anthropic.com/en/docs/claude-code/skills)와 [OpenAI Codex](https://developers.openai.com/codex/)용). 관현악법·화성·악식·대위법·믹싱·장르 실무를 다룬 책 50권과, 멀티트랙 음원에서 실측한 편곡 62곡에서 뽑아냈습니다.

`SKILL.md`는 공개 규격 [agentskills.io](https://agentskills.io)를 따르며, 두 에이전트가 같은 파일을 공유합니다. 한 번 설치하면 양쪽에서 그대로 작동합니다.

**나오는 것은 조언이 아니라 한 장의 사양서입니다.** 곡을 요청하면 에이전트가 채우는 것은 ARR-SPEC입니다 — 조성, 템포, 마디 단위 섹션 맵, 코드네임과 로마숫자 도수, 누가 언제 들어오고 언제 빠지는지, 에너지 커브, 보컬을 어떻게 부르게 할지, 믹스 의도. 그리고 바로 그 문서 하나를 Suno 프롬프트로, YuE2용 ABC 악보로, 또는 MIDI로 컴파일합니다. 결과물을 검수할 때 대조하는 것도 같은 문서입니다. 설계는 이 한마디로 끝납니다 — **하나의 산출물을 네 가지로 쓴다**: 외부 인수인계, 조건을 맞춘 A/B, 컴파일 원본, 수용 기준.

**자기 언어로 물어보세요.** 스킬 본문은 중국어로 쓰여 있습니다. 저본 대부분이 중국어 원저이거나 중국어 번역본이기 때문입니다. 어떤 언어로 묻든 에이전트는 그 언어로 답합니다.

**이 스킬은 생성 모델을 빠르게 만들지 않습니다. 시간을 들여 품질을 얻는 방식입니다.** 전문 음악 작업 워크플로를 한 번 온전히 돌리면 한 곡에 20분 이상 걸리는 일도 흔합니다(agent가 판단 기준을 읽고, 규격서를 채우고, 자체 점검을 거치기 때문입니다). 그 대가로 얻는 것은 몇 줄의 프롬프트가 아니라 전문가 수준의 규격서입니다.

**이 라이브러리는 어떤 작품도 담고 있지 않습니다. 저자 본인의 것도, 다른 가수의 것도, 편곡도 가사도 없습니다.** 음악 작품의 좋고 나쁨은 주관적인 판단입니다. 직접 써 보고, 이 도구의 가치와 시간이라는 비용을 스스로 판단해 주십시오.

## 이 시리즈의 네 라이브러리

하나의 오디오 라인을 독립된 네 라이브러리로 나누었습니다. 각각 단독으로 쓸 수 있고, 이음새가 문서화되어 있어 조합해서도 씁니다.

| 라이브러리 | 하는 일 | 상태 |
|---|---|---|
| **[music-composition-skills](https://github.com/jtydhr88/music-composition-skills)** | 작곡과 편곡. 브리프를 ARR-SPEC으로 바꿉니다: 조, 템포, 섹션 표, 화성, 누가 언제 들어오고 나가는지, 에너지 곡선, 보컬과 믹스 의도. Suno, YuE2, MIDI용 입력으로 컴파일 | **이 라이브러리** |
| **[lyric-writing-skills](https://github.com/jtydhr88/lyric-writing-skills)** | 작사. 입의(立意) 관문을 LYR-SPEC으로 바꿉니다: 구조, 이미지, 운, 서술, 그리고 중국어(보통화·광둥어), 영어, 일본어, 한국어의 언어 층 | 공개됨 |
| **영화 음악** | 영상에 맞춰 쓰는 음악: 스포팅, 컷과의 관계, cue를 쓰고 이름 짓는 법, 테마가 영화 전체에서 발전하는 방식 | 예정 |
| **믹싱과 사운드 디자인** | 믹스 의도를 실제 조작으로 바꾸기: EQ, 컴프레션, 리버브, 오토메이션, 마스터링 | 예정 |

**독립적입니다.** 기존 멜로디에 가사를 붙이려면 작사 라이브러리만 있으면 됩니다. 연주곡을 편곡하려면 작편곡 라이브러리만 있으면 됩니다.

**이름 붙은 인계로 조합됩니다.** ARR-SPEC과 LYR-SPEC은 양방향입니다. 곡이 먼저면 섹션 표와 마디 수를 넘기고, 가사가 먼저면 행 길이와 강세 위치를 돌려주며, 여섯 필드는 양방향에서 일치해야 합니다. ARR-SPEC 안의 `mix_intent`는 믹싱 라이브러리가 브리프로 받는 것이고, 영화 음악 라이브러리의 cue sheet는 작편곡 라이브러리가 브리프로 받는 것입니다.

**이음새는 이미 쓰여 있습니다.** 모든 스킬이 경계 표를 갖고 있어, 다른 라이브러리에 속한 질문은 그 자리에서 어설프게 답하지 않고 이름으로 넘깁니다. 그래서 예정된 두 라이브러리가 이미 곳곳에서 언급됩니다: EQ와 컴프레션 실무는 믹싱 라이브러리로, 스포팅과 cue 작성은 영화 음악 라이브러리로.

## 생성 모델이 있는데 왜 이 스킬이 필요한가

Suno와 YuE2는 이미 한 문장을 그럴듯하게 완성된 한 곡으로 바꿔 줍니다. 이들이 하지 못하는 것은, 하나의 지시를 두 번 똑같이 돌려주는 일입니다.

생성 모델은 당신이 지정하지 않은 부분을 전부 채웁니다. 그것도 자기 기본값으로 채웁니다. 사람들이 "AI 냄새"라고 듣는 것이 바로 그 기본값입니다 — 모든 섹션이 8마디의 배수, 에너지는 오르기만 하고, 벌스에서 후렴까지 편성이 한 번도 바뀌지 않고, 끝은 페이드아웃, 보컬은 처음부터 끝까지 한 가지 세기. 이것은 모델의 결함이 아닙니다. 아무도 결정을 내리지 않은 소리입니다.

이 라이브러리가 공급하는 것이 바로 그 결정입니다. 현업 편곡자가 내리는 수준으로 정하고, 모델에게 전달할 수 있는 형태로 적어 둡니다 — 기타가 몇 번째 마디에서 빠지는지, 어느 섹션이 올라가기 직전에 한 겹을 덜어내는지, 에너지가 어디서 떨어지는지, 세 번째 후렴에서 보컬이 무엇을 달리하는지. **하는 일은 전문가 수준의 규칙으로 생성 모델을 디렉션하는 것입니다. 생성 모델을 다시 만들려는 시도가 아닙니다.**

그렇게 해서 얻는 것은 프롬프트 엔지니어링이 닿지 못하는 부분입니다. 프롬프트는 한 문장이고, 한 문장은 필드별로 대조할 수 없습니다. 사양서라면 돌아온 결과와 필드 단위로 맞춰 볼 수 있고, 한 번에 한 필드만 바꿔 다시 돌려서 통제된 비교를 할 수 있습니다. 거기 적힌 모든 결정에는 이유와 출처가 붙어 있으므로, 반년 뒤에도 두 번째 후렴을 왜 그렇게 편곡했는지 말할 수 있습니다.

모델은 여전히 연주자이고 스튜디오입니다. 이것은 그 손에 건네는 편곡 악보입니다.

## 설치

### Claude Code

#### 플러그인 마켓플레이스(권장)

```
/plugin marketplace add jtydhr88/music-composition-skills
/plugin install music-composition@music-composition-skills
```

이후에는 `/music-composition:<skill>`로 호출합니다. 예: `/music-composition:mc-workflow`.

#### 개인용(모든 프로젝트)

```bash
git clone https://github.com/jtydhr88/music-composition-skills.git
cp -r music-composition-skills/plugins/music-composition/skills/* ~/.claude/skills/
```

#### 프로젝트별

```bash
mkdir -p .claude/skills
cp -r music-composition-skills/plugins/music-composition/skills/* .claude/skills/
```

### Codex(CLI / ChatGPT 데스크톱 앱 / IDE 확장)

```bash
codex plugin marketplace add jtydhr88/music-composition-skills
# 그다음: Plugins → "Music Composition Skills" 선택 → Install
```

또는 같은 파일들을 `~/.agents/skills/`(개인용)나 `.agents/skills/`(프로젝트용)에 복사하세요. 동일한 29개 `SKILL.md`가 양쪽 플러그인 디렉터리를 통해 배포되며, 중복도 재작성도 없습니다.

#### 확인

관련 맥락을 감지하면 스킬은 자동으로 로드됩니다. 목록을 보려면 `/skills`.

## 자주 쓰는 조합

겉보기보다 복잡합니다. 한 줄짜리 brief가 작곡·편곡·작사 세 방면에서 십여 개 skill을 움직이고, 에이전트가 무엇을 읽고 무엇을 내놓는지는 그 한 줄에 핵심 항목 몇 가지가 들어 있는지로 정해집니다. 아래는 실제로 끝까지 돌려 본 조합입니다. 어떻게 말하는지, 어느 skill을 지나는지, 무엇이 나오는지. 가사가 있는 용례는 작곡편곡 라이브러리와 작사 라이브러리를 둘 다 설치해야 합니다.

**1. 특정 가수의 스타일로 가사 있는 곡 쓰기**(가장 흔함)

> 어떤 가수의 어떤 곡 같은 스타일의 중국어 팝 한 곡, 여성 보컬, Suno로 생성, 가사 포함.

지남: lw-workflow → lw-song-intent → lw-structure → lw-mandarin → lw-tone-check → lw-suno-interface; mc-workflow → mc-style-chinese-pop → mc-melody → mc-development → mc-arrangement-arch → mc-vocal-direction → mc-render-compile
산출: LYR-SPEC.yaml, ARR-SPEC.yaml, suno-pack.md(제목, 스타일 설명, 섹션 태그 붙은 가사, 제외어)
비고: 참조 가수에게서 빌리는 것은 편성·템포·보컬 페르소나·섹션 진행뿐입니다. 가사와 멜로디는 빌리지 않습니다.

**2. 抖音용 중독성 있는 곡, 서사 없이**

> 抖音용 중독성 있는 곡 한 곡, 여성, 달콤하게, 서사는 없이. Suno 생성, 가사 포함.

지남: lw-song-intent(태도형) → lw-structure(반복 예산, 훅 위치) → lw-rhyme → lw-mandarin; mc-style-chinese-pop → mc-rhythm-groove → mc-arrangement-arch → mc-render-compile
비고: "서사는 없이" 한마디가 가사 유형을 정합니다. 말하지 않으면 기본값은 정경형입니다.

**3. 슬픈 사랑 노래, 직접 말하기, 장면 없이**

> 어떤 가수의 어떤 곡 같은 슬픈 사랑 노래, 남성 보컬, Suno 생성, 가사 포함. 직접 말하는 쪽으로, 장면 묘사는 없이.

지남: 1과 같되 lw-song-intent가 태도형으로 가고, 닻은 물건이 아니라 한 문장(후렴마다 첫머리에 반복되는 행); mc-vocal-direction이 온마이크 남성 보컬과 마지막 한 줄의 여백을 맡음
비고: 코퍼스에서 태도형 곡의 열에 넷은 사진으로 찍을 수 있는 물건이 하나도 없습니다. 후렴은 "너"에게 하는 한 문장, 벌스는 나의 상태, 첫 줄은 독백. 이걸 원하면 brief에 "직접 말해, 장면도 물건도 없이"라고 씁니다.

**4. 하나의 기분, 이야기로 만들지 않기**

> 중국어 팝 한 곡, 3분 30초, 여성 보컬. 주제는 이사하던 날 충전 케이블을 벽 콘센트에 꽂아 둔 채 나와서 두 블록을 걷고서야 생각났는데 돌아가지 않은 것. 이야기로 쓰지 말고, 생각났다가 그냥 두는 그 기분을 원해.

지남: lw-song-intent(정경형, 닻 물건은 케이블) → lw-imagery → lw-structure → lw-mandarin → lw-tone-check; 곡 쪽은 1과 같음
비고: 정경형과 서사형의 경계가 여기입니다. 물건은 있고, 줄거리는 진행하지 않습니다.

**5. 연주곡, 처음부터 작곡**

> 2분 40초짜리 연주곡, 쇼트 영상 배경용. 주선율은 나일론 현 기타, 약간의 타악과 베이스, 건반 한 대까지 허용. 느낌은 "오후 세 시, 누군가를 기다리는데, 급하지 않다". 보컬 없음.

지남: mc-workflow → mc-development(동기, 성격, 전개 수법) → mc-melody → mc-form → mc-harmony → mc-rhythm-section → mc-orchestration → mc-render-compile
산출: ARR-SPEC.yaml(material 블록과 섹션별 development 채움), suno-pack.md, 한 쪽짜리 설명
비고: 가사가 없으므로 작사 라이브러리는 관여하지 않습니다. 판정 기준은 mc-development에 있습니다. 새 재료는 절반 미만, 재현 있음.

**6. 가사와 멜로디는 있고, 편곡만**

> 멜로디와 가사가 이미 있는 중국어 사랑 노래를 편곡해 줘. 살사 느낌, 브라스 포함, 중간보다 조금 빠르게. 사양서만, Suno 프롬프트는 필요 없음.

지남: mc-workflow(편곡 경로) → mc-style-latin → mc-rhythm-section → mc-orchestration(브라스) → mc-arrangement-arch → mc-texture-layering
산출: ARR-SPEC.yaml과 한 쪽짜리 설명뿐

**7. 융합: 벌스는 랩, 후렴은 중국풍**

> 어떤 곡 같은 랩 더하기 중국풍 곡, 완전한 중국어 가사, Suno용.

지남: mc-workflow §2.4 스타일 융합 → mc-style-hiphop(베이스) + mc-style-chinese-pop(오버레이); lw-rap(벌스) + lw-chinese-style(후렴) + lw-mandarin

**8. 광둥어 가사를 주어진 멜로디에**

> 이 멜로디에 광둥어 가사를 붙여 줘. 마디 수와 행마다 음절 수는 첨부.

지남: lw-workflow(곡 먼저) → lw-cantonese(먼저 음높이 부류로 계산, 그다음 글자 선택) → lw-tone-check
비고: 광둥어는 쓰는 순서가 거꾸로이며 표준중국어 층으로 대체할 수 없습니다.

**9. Suno 대신 로컬 오픈소스 모델(YuE2)**

> 같은 곡을 Suno 없이 로컬 YuE2로 생성하고 싶어. 사양서를 ABC 악보로 컴파일해 줘.

지남: 1과 같고, 여기에 mc-symbolic-score(ARR-SPEC을 ABC로 컴파일, 보컬 라인은 소문자 음이름 음역에, w: 가사 행 포함)

## 별도 도구가 필요 없습니다

플러그인은 순수 텍스트입니다. 실행할 스크립트도, Python도, Node도, lint 단계도 없습니다. 이 라이브러리의 모든 점검 항목은 당신이나 에이전트가 눈으로 훑을 수 있는 **체크리스트**로 존재합니다 — `mc-workflow` §3.0의 20항목 사양 자체점검, `mc-ai-tell-audit`의 14개 AI 냄새 플래그, 각 스킬 끝의 "끝내기 전에 반드시 통과할 것" 목록.

**규칙은 판단 기준이지 관문이 아닙니다.** 어떤 점검이 통과하지 못하면, 사양을 바꾸든지 아니면 이 곡은 왜 그래야 하는지 한 줄 적으면 됩니다. 이유를 적은 일탈은 정당한 선택입니다. 이 라이브러리에는 컴파일을 막는 장치가 하나도 없습니다.

## 다국어 지원

**소스는 하나, 출력은 런타임에 어떤 언어로든.** 스킬은 중국어로 딱 한 번 쓰여 있고, 에이전트는 당신이 물어본 언어로 답합니다. 플래그도, 별도 설치도, 언어별 플러그인도 없습니다.

스킬 본문을 다른 언어로 갈라 두지는 않습니다. 이것은 누락이 아니라 결정입니다. 자매 프로젝트 [screenwriting-skills](https://github.com/jtydhr88/screenwriting-skills)는 완전한 영어판을 만들어 본체에 합쳤다가 나중에 지웠고, 그때 결론을 낸 논거가 여기에도 그대로 적용됩니다 — 중국어를 읽지 못하는 사람에게 번역본이 필요하다면 영어를 읽지 못하는 사람에게도 필요하고, 그다음은 일본어, 그다음은 한국어, 이어서 프랑스어입니다. 이 팩은 파일 52개입니다. 네 언어면 208개가 되고, 각자 따로 어긋나며, 어느 쪽이 낡았는지 알려 주는 장치는 아무것도 없습니다. 번역 자체는 싼 쪽입니다. 진짜 비용은, 한 번 갈라놓고 나면 두 번째 분기를 거절할 원칙적 근거가 사라진다는 점입니다.

그 몫을 런타임이 이렇게 대신 감당합니다.

- **출력 언어는 질문의 언어를 따릅니다.** 한국어로 물으면 한국어로 옵니다. 편곡 악보도, 섹션 이름도, 그렇게 판단한 근거도 그 언어로 돌아옵니다.
- **용어는 원어에 고정합니다.** 이 분야의 어휘는 애초에 영어·이탈리아어·독일어·일본어가 뒤섞여 있습니다 — *tension*, *avoid note*, *comping*, *build*, *drop*, 落ちサビ, 打ち込み. 저본의 중국어 자체가 번역어이고 역자마다 선택이 달랐기 때문에, 원어가 개념과 함께 움직입니다.
- **대응하는 번역어가 없는 용어는 원형에 주석을 붙여 둡니다.** 落ちサビ, 符割り, 類音階, 十三辙(중국어 압운 분류)은 원어에 짧은 설명을 단 형태로 나옵니다.
- **당신의 악보와 가사는 원래 언어 그대로입니다.** 중국어 노래를 영어로 논하는 것은 평범한 일입니다. 바뀌는 것은 대화의 언어이지, 작품이 아닙니다.

이 선택이 대가로 내주는 것은 감사 가능성(auditability)입니다. 중국어를 읽지 못하면 지시 파일 자체는 읽을 수 없고, 에이전트가 그것을 옮겨 말한 내용만 읽게 됩니다. 이것은 실제로 치르는 비용이며, 번역본이 진짜로 사 올 수 있는 것도 딱 그 하나입니다. 그럼에도, 모든 규칙이 검증 가능한 출처와 쪽수를 달고 있다는 데 가치의 근거를 둔 라이브러리에서, 네 갈래를 영구히 유지하는 부담만큼의 값어치는 없습니다.

**README는 경우가 다릅니다.** README는 번역했습니다. 짧고, 내용이 안정적이며, 새로 온 사람이 가장 먼저 마주치는 것이기 때문입니다.

## 스킬 구성

여섯 개 층입니다. 위층은 자기 아래층만 알고, 모든 스킬은 자기가 **맡지 않는** 것을 명시한 경계표를 지닙니다 — 스타일 층이 일반 화성을 슬쩍 고쳐 쓰지 못하게 막는 것이 바로 그 표입니다.

```
L0 워크플로     라우터, ARR-SPEC 계약, 융합 시 담당 분담, 단계표
L1 일반층       멜로디 · 화성 · 코드 진행 · 전조 · 리듬 · 악식 · 대위법
L2 편곡층       구조 · 오케스트레이션 · 텍스처 · 리듬 섹션 · 사운드 디자인 · 보컬 · 믹스 의도
L3 스타일층     J-POP · 시티팝 & R&B · 재즈 · 중화권 팝 · EDM · 록 밴드 · 시네마틱 · 힙합
L4 실행층       각 백엔드로 컴파일 · 기호 악보 · AI 냄새 진단
L5 코퍼스층     교과서의 규칙을 뒷받침하거나 반증하는 실측 음원
```

### L4 — 실행과 검증

| 스킬 | 무엇을 다루는가 |
|---|---|
| `mc-render-compile` | 컴파일러는 하나, 백엔드는 여럿. 백엔드 차이는 **데이터**로 `backends.yaml`에 둔다 — 각 백엔드가 필드마다 `honors: exact / hint / none`을 선언하고, 이행할 수 없는 필드는 **0점을 주는 대신 채점에서 제외한다**. 모델을 하나 더하는 것은 스킬이 아니라 데이터 블록을 하나 더하는 일 |
| `mc-symbolic-score` | ARR-SPEC을 ABC, MusicXML, MIDI로 하나의 이미터에서 출력. 이 경로에서 사양은 "암시"되는 것이 아니라 **실행**된다 |
| `mc-ai-tell-audit` | 기계가 만든 음악에 나타나는 열거 가능한 징후 14가지를 하나씩 센다. 두 숫자를 일부러 분리해 둔다: *백엔드가 사양대로 했는가*와 *결과물에 기계 지문이 남았는가* — 앞쪽이 만점이어도 뒤쪽에서 떨어지는 트랙이 있다 |

### L5 — 코퍼스

| 스킬 | 무엇을 다루는가 |
|---|---|
| `mc-case-studies` | 음원에게 증언시키는 방법. 멀티트랙 음원에서 실측한 편곡 62곡을 ARR-SPEC으로 되받아 적어 두었기에, 교과서의 주장을 의견이 아니라 적중률과 대조할 수 있다. 큐레이션이 아니라 자연 표집 — 코퍼스를 큐레이션하면 이미 믿고 있는 규칙 쪽으로 편향된다 |
